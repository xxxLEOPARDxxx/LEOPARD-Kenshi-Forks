This can help character assets once native requests actually use those cached files, but it is not proof of preprocessing character bodies or warming all dependencies. The new forward manifest only copies terrain files (resource_forward.cpp:93) and only queues terrain GPU jobs. It does not predict character/squad asset dependencies.

## Owned preparation boundary and exclusions

The presently demonstrated safe preparable data is immutable asset bytes and copied terrain resource names/metadata. An eventual character-asset manifest must capture logical mesh/skeleton/material/texture identities on their owner thread into bounded owned data, preserve native archive/group resolution, and let native completion adopt matching results. Appearance.h:119,123,126-130 already exposes body construction, entity callbacks and per-character materials; these are evidence of callback ownership and individualized state, not permission to call them on a worker. RootObjectFactory.h:47,49 contains createRandomUnloadedCharacter/Squad but those methods still accept Faction, ownership, town, squad and GameData state. The word unloaded does not prove pure/thread-safe construction and must not be used as an offload contract.

Keep live factory, handles, faction/platoon membership, RNG-driven generation, appearance callbacks, scene objects, physics creation and AI registration on their established native owners. The existing first-time/town rule is especially relevant: zone_first_time.cpp:29-39 documents native phase-B collectBuildings -> barflies and chooseResidents -> populateBuilding. preload_prepare.cpp:134 deliberately returns those cells untouched to the game. Moving processContent or bypassing native readiness previously risked missing residents/placement errors. Its ordinary saved-content finalize is a geometry mutation at preload_prepare.cpp:22-31, not a pure parser.

There is no verified GPU kernel/adoption contract for character generation here. GPU resource preparation can remove some data preparation/upload cost only when the real consumer reuses it; it does not execute the CPU object's registration/AI/physics lifecycle. Existing terrain gpuCreated with adopted=0 establishes no speedup and says nothing about NPC spawning.
